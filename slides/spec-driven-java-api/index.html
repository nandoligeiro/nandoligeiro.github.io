Princípio
Spec-Driven Development

A especificação deixa de ser documentação passiva e passa a governar a implementação.

O humano define intenção, regras e critérios. O agente transforma artefatos consistentes em código verificável.

Especificar não é escrever tudo; é tornar decisões explícitas03 / 14
A palavra importante é governar. O spec não é um PDF esquecido: ele participa do fluxo, gera plano e tarefas e volta na validação.

1 · Constitution
Regras inegociáveis

Antes do endpoint, definimos como este sistema deve existir.

Constitution não deve virar mural de frases bonitas. Cada princípio precisa alterar decisões ou gerar uma verificação concreta.
2 · Specify
O quê e por quê
Tecnologia fica fora desta conversa

O spec descreve comportamento observável, não classes Java.

Cenário principal

Dado um cartão ativo, quando o cliente solicita um limite permitido, então o novo limite é confirmado.

Retentativa

A mesma chave e o mesmo payload retornam o resultado anterior, sem nova alteração.

Conflito

A mesma chave com payload diferente retorna 409 e preserva o estado original.

Critérios de aceite tornam a intenção verificável antes de escolher framework ou banco.

O spec fala a língua do produto e do contrato07 / 14
Faça o contraste: “crie um CardLimitController” já escolhe solução. “ajuste o limite sem duplicar efeitos” descreve o comportamento que importa.
Clarify
Perguntar antes de inventar
A ambiguidade mais cara é a que parece detalhe

O que significa repetir uma chave de idempotência?

Mesma chave + mesmo payload

Retornar exatamente a decisão já persistida.

Mesma chave + payload diferente

Responder HTTP 409 com código IDEMPOTENCY_CONFLICT.

A resposta entra no `spec.md`. A IA não guarda a decisão “na cabeça”.

Clarificar cedo custa minutos; corrigir semântica em produção custa história08 / 14
Aqui está um ótimo exemplo de pergunta que muda banco, contrato, testes e tratamento de erro. Sem resposta, qualquer implementação parece plausível.

4 · Tasks

O plano vira trabalho observável

Cada tarefa tem dependência, arquivo e evidência de conclusão.

FASE B · DOMÍNIOT04–T07

Analyze
Sanidade antes do código
Leitura cruzada e sem mutação

Spec, plano e tarefas contam a mesma história?

CRÍTICO

O spec exige idempotência, mas nenhuma tarefa cria persistência da chave.

MÉDIO

O contrato retorna 202, enquanto o cenário principal promete confirmação síncrona.

PASS

A regra de não registrar dados sensíveis aparece no plano e nos testes.

`/speckit.analyze` procura lacunas, inconsistências e cobertura antes da implementação.

Diagnóstico barato antes do patch caro11 / 14
O analyze não substitui revisão humana. Ele cria um ponto de controle explícito para corrigir artefatos enquanto a mudança ainda é texto.
Implement + Converge
Código e evidência
Agora a IA escreve a sintaxe

Implementar é executar tarefas; convergir é provar aderência.

O agente não “termina porque parece pronto”. Ele compara código, testes e artefatos até não haver trabalho relevante pendente.
